# Contributing to mcx-anonymizer

Thank you for your interest. This project anonymises captures from
safety-critical networks, so the rules below are strict. Please read them before
opening a pull request.

## Contributor Licence Agreement

mcx-anonymizer is dual-licensed: GPL-3.0-or-later and a commercial licence. To
keep that possible, every external contribution needs a signed Contributor
Licence Agreement ([CLA.md](CLA.md)). A check on each pull request asks you to
sign it once by posting a comment.

## Clean-room rule

Write every line yourself, from the published standards (IETF RFCs and drafts,
IEEE, 3GPP, ETSI). Do not copy, translate or adapt code from Wireshark, tcpdump,
other anonymisers or any Mission Critical product, whatever its licence. Rules
in `rules/*.yaml` cite the clause of the standard they implement
(`source: {spec, version, clause}`); `rules/SOURCES.md` lists the document
versions.

New dependencies must be under a permissive licence: MIT, BSD-2-Clause,
BSD-3-Clause, Apache-2.0 (also with the LLVM exception), BSL-1.0, Unlicense or
zlib. GPL, LGPL and AGPL dependencies are not accepted. `tools/check-licenses.py`
enforces this.

## Tests first

Every change starts with a failing test:

- unit tests (Catch2) in `tests/unit/`;
- integration tests (Python, standard library only) in `tests/integration/`;
- fuzz targets in `tests/fuzz/` for every parser of untrusted input.

A new protocol field needs a rule, a dissector entry, a canary in the fixture
generator that proves the original value is absent from the output, and an
integrity check that the output still decodes.

## Adding a SIP header, SDP attribute, feature tag or body type

Whatever the SIP layer keeps, it keeps because a rule says so; everything without
a rule is removed. A new entry is a rule, a verified source and a canary, in one
pull request.

1. **Find the definition in the standard.** Read the clause that defines the
   header, parameter, attribute, tag or body type in the published document
   (RFC, 3GPP or ETSI specification). Note the specification, its version
   (RFC publication month, or the 3GPP version number) and the clause. Sources
   come from the standards only: not from another implementation, a capture, a
   vendor document or a summary of a standard. If the clause is ambiguous, say so
   in the pull request instead of guessing.
2. **Register the document.** The document must be listed in the SIP section of
   `rules/SOURCES.md`. The rule loader accepts only those documents
   (`src/policy/sip_rules.cpp`, lists `kRfcs` and `k3gpp`); add a new one to both
   in the same change.
3. **Write the rule** in the file for its kind, with
   `source: {spec: ..., version: ..., clause: ...}`:
   - a header in `rules/sip-headers.yaml`: its grammar, `keep`, `pseudonymise`
     (with the category of each component) or `remove`, and every header
     parameter with its own action and source. Choose `keep` only for values
     that cannot identify a user, a device, a network or a site;
   - a URI parameter in `rules/sip-params.yaml`;
   - an SDP line or attribute in `rules/sdp.yaml`, with the action of each field;
   - a media feature tag, feature-capability indicator, ICSI or IARI in
     `rules/sip-feature-tags.yaml`;
   - a body type in `rules/sip-bodies.yaml` (`sdp`, `multipart` or emptied).
4. **Plant a canary.** Every rule whose action is not `keep` needs a synthetic
   value in `tools/fixturegen/sip.py`, registered with its rule key
   (`sip:<Header>.<component>`, `sip-param:<Header>;<param>`, `uri-param:<name>`,
   `sdp:<line or a=attribute>[.<field>]`, `tag:<feature-tag>`,
   `body:<content-type>`; see `tools/fixturegen/canary.py`). The
   `rule-canary-coverage` test fails while a rule has no canary, and the SIP
   integration tests fail if a canary survives in any output.
5. **Keep the scanner in step.** The scanner keeps its own table of the names
   the output keeps on purpose (`src/scan/walker/sip_vocabulary.cpp`); a unit
   test checks it against the rule set, so add the new name there. If the new
   header carries an identity that the scanner's own harvester does not extract
   yet (`src/scan/walker/sip_harvest.cpp`), extend the harvester with its own
   minimal tokenizer: it must not share code with the anonymiser.
6. **Check the output decodes.** Run the integrity tests with `tshark`
   installed (`MCXANON_REQUIRE_TSHARK=1`): no new expert errors, the same SIP
   ladder, and the SDP-announced RTP flows still set up.

## Test data: synthetic only

Never add a real packet capture, a pseudonym mapping, a project secret or any
value taken from a real network to the repository, not even in a test, comment
or issue. Test captures are generated by `tools/fixturegen/` from documentation
address ranges. The leak guard rejects capture files, mappings and secrets;
enable it once per clone:

```bash
git config core.hooksPath .githooks
```

CI runs the same check on every push.

## Building and testing

Build and test inside the reference container so that results are
reproducible:

```bash
docker build -t mcxanon-ci .ci
docker run --rm -v "$PWD:/work" -w /work mcxanon-ci bash .ci/build.sh gcc14 test
docker run --rm -v "$PWD:/work" -w /work mcxanon-ci bash .ci/build.sh clang19 test
docker run --rm -v "$PWD:/work" -w /work mcxanon-ci bash .ci/build.sh asan test
docker run --rm -v "$PWD:/work" -w /work mcxanon-ci bash -c \
  '.ci/build.sh fuzz && tools/run-fuzzers.sh 60 build/Debug'
```

A pull request is ready when all of these pass, including the `gate` tests
(licences, scanner independence, public headers, SPDX headers).

The scanner in `src/scan/` must stay independent of the anonymiser: it may only
use `src/bytes/`. `tools/check-scan-independence.sh` enforces this.

## Code style

- C++23, formatted with `.clang-format`, checked with `.clang-tidy`.
- No exceptions across the public API; fallible calls return `Result<T>`.
- Error messages and reports never contain original values.

## Licence header

Every source, build, script and configuration file starts with an SPDX licence
identifier (after the shebang line, if any):

```cpp
// SPDX-License-Identifier: GPL-3.0-or-later
```

Use `#` comments in CMake, Python, shell and YAML files. `tools/check-spdx.sh`
checks this; documentation and JSON files are exempt.

## Language

Code, comments, commit messages, documentation and issues are in English.
